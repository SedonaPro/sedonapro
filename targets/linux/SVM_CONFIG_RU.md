# Конфигурация SVM (этапы 1–3)

Все возможности необязательны. Без конфигурации VM ведёт себя как раньше,
кроме часов: по умолчанию теперь `clock=monotonic`.
Checksum ни одного kit не изменился: manifests, редакторы (Niagara, MCS,
sedona-web) и существующие `app.sab` совместимы. На этапе 3 в `sys::App` добавлен
нерефлексивный нативный метод `scanResync` (id 0::62). Он не входит в checksum,
но `kits.scode`, собранный из нового `sys`, требует `svm` этапа 3 или новее.
Старый `svm` с таким образом остановится с ошибкой 12 (missing native).

## Где задаётся

По возрастанию приоритета:

1. значения по умолчанию;
2. файл: `--config=<путь>`, иначе `$SVM_CONFIG`, иначе `./svm.conf`, если он есть
   (каталог после `--home=`);
3. переменные окружения `SVM_<КЛЮЧ>`: точки заменяются на `_`, всё в верхнем регистре,
   например `SVM_STAGE_ROLLBACK=1`;
4. командная строка: `--opt=<ключ>=<значение>`, можно повторять.

Формат файла: `ключ = значение`, комментарии `#` или `;`. Если ключ неизвестен
или значение неверно, VM не запускается и завершается с кодом 30
(`ERR_INVALID_CONFIG`). Действующие значения печатаются при старте после версии.
Пример: `svm.conf.example`.

## Параметры

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `clock` | `monotonic` | `monotonic`: `Sys.ticks` по `CLOCK_MONOTONIC` с наносекундной точностью, `Sys.sleep` через `clock_nanosleep` с продолжением после сигналов. `legacy`: прежний `times()` с шагом 10 мс. |
| `stack.cells` | `4096` | Стек VM в ячейках (8 байт на amd64). |
| `stage.validate` | `0` | Проверка `*.stage` перед установкой. scode: magic, версия, blockSize, refSize, размер из заголовка. sab: `sapp`, версия 3, маркер конца `.`. Если хотя бы один файл плохой, отклоняется **вся** пара: файлы переименовываются в `*.rejected`, VM работает на прежних. |
| `stage.rollback` | `0` | Пробный период обновления, см. ниже. |
| `stage.trial.seconds` | `120` | Сколько секунд цикл сканирования должен проработать, чтобы обновление было принято. |
| `stage.trial.attempts` | `3` | Сколько запусков процесса допускается в пробном периоде. |
| `save.atomic` | `0` | Атомарная запись файлов с суффиксами `save.atomic.suffixes`, см. ниже. |
| `save.atomic.suffixes` | `.sab` | Суффиксы через запятую. |
| `save.keep` | `1` | Сколько поколений резервной копии хранить при `App.save`: `app.sab.bak`, `app.sab.bak.1` … `app.sab.bak.<N-1>`. `1` — как раньше, только `app.sab.bak`. |
| `watchdog` | `auto` | `auto`: пинговать systemd, только если unit задаёт `WatchdogSec` (переменная `WATCHDOG_USEC`); `1`: всегда (если есть `NOTIFY_SOCKET`); `0`: никогда. Пинг идёт только из цикла сканирования, так что зависший цикл или service `work()` перестаёт пинговать. |
| `watchdog.seconds` | `10` | Интервал пинга при `watchdog=1`, если systemd не передал свой (иначе берётся половина `WatchdogSec`). |
| `stats.interval` | `0` | Раз в N секунд печатать статистику цикла: число циклов, период (среднее/мин/макс), переполнения, максимальное опоздание. `0` — выключено. |
| `stats.file` | — | Дополнительно записывать последний отчёт в файл (`ключ=значение`, атомарно). |
| `safeboot.after` | `0` | Безопасный запуск после N неудачных запусков подряд, см. ниже. `0` — выключено. |
| `safeboot.healthy.seconds` | `60` | Сколько секунд цикл сканирования должен проработать, чтобы запуск считался удачным. |
| `safeboot.app` | — | Приложение для второго уровня safeboot. |
| `rt.mlockall` | `0` | Закрепить память VM в RAM (`MCL_ONFAULT`: стеки потоков не закрепляются целиком). |
| `rt.sched` | `other` | `fifo:N` или `rr:N` (N = 1..99): политика планировщика реального времени. |
| `rt.cpus` | все | Список CPU, например `1` или `0,2-3`. |
| `rt.strict` | `0` | `1`: не запускаться (код 31), если какую-то rt-настройку применить не удалось. По умолчанию только предупреждение. |
| `scan.resync` | `off` | Что делать с циклом сканирования после перегрузки. `off`: как раньше, пропущенные циклы догоняются серией без пауз. `skip`: пропущенные периоды отбрасываются, следующий цикл идёт по исходной сетке. `now`: следующий цикл начинается сразу, сетка сдвигается. |
| `scan.resync.periods` | `1` | Срабатывать, только если отставание не меньше N полных периодов. Меньшие опоздания компенсируются как раньше: средняя частота сохраняется. |
| `modbus.safe` | `0` | Modbus Master: освобождать регистры удалённых точек и не терять изменения адреса, функции или длины, сделанные во время запроса. См. ниже. |
| `mem.fixes` | `0` | Освобождать память, которую исходный код теряет: лексер выражений `sproExpr` при синтаксической ошибке и таблицу регистров Modbus Slave (~20 КБ) при удалении сервиса. |
| `crash.handler` | `0` | При SIGSEGV, SIGBUS, SIGFPE, SIGILL или SIGABRT печатает сигнал и native backtrace в stderr, затем завершается тем же сигналом. Код выхода, core dump и `Restart=` systemd работают как без обработчика. Адреса расшифровываются так: `addr2line -f -e svm 0x<смещение>`. |

## Адрес привязки сокетов (`SVM_INET_BIND`)

Только переменная окружения, в `svm.conf` не задаётся. По умолчанию VM слушает SOX,
веб и прочие серверные сокеты на всех интерфейсах. `SVM_INET_BIND=127.0.0.1` привязывает
их к одному адресу IPv4: такая VM недоступна из сети. Так запускает свой симулятор
Sedona Studio. Значение, не являющееся адресом, приводит к ошибке привязки, а не к
прослушиванию всех интерфейсов. Исходящие соединения не затрагиваются.

## Пробный период обновления (`stage.rollback=1`)

Применяется при установке `kits.scode.stage` и/или `app.sab.stage`, как при
запуске, так и при `App.restart`:

1. Создаётся маркер `svm.trial`.
2. Текущие файлы сохраняются как `*.lkg`. `app.sab.lkg` создаётся всегда, потому что
   новые kits могут перезаписать приложение.
3. Новые файлы устанавливаются атомарным `rename`.
4. Если цикл сканирования проработал `stage.trial.seconds`, печатается
   `svm update trial: update accepted`, а маркер удаляется. Файлы `*.lkg` остаются до
   следующего обновления.
5. Откат выполняется, если в пробный период:
   - VM завершилась с ошибкой (например, `Schema mismatch`, «Cannot run VM»). Откат идёт
     сразу, без выхода из процесса, и VM запускается на прежних файлах;
   - процесс запускался больше `stage.trial.attempts` раз (падение, kill, перезапуск systemd).
     Откат выполняется при следующем запуске.

   При откате: неудачные файлы переименовываются в `*.failed`, `*.lkg` возвращаются
   на место, оставшиеся `*.stage` переименовываются в `*.rejected`.

Ограничение: если VM зависла (бесконечный цикл), это пока не обнаруживается.
Нужен systemd watchdog, он запланирован на этап 2.

## Цикл сканирования

Статистика, watchdog, пробный период и safeboot привязаны к сну **цикла
сканирования** (`sys::App.resumeApp`), а не к любому `Sys.sleep`. Штатная
`sproPlatformLinux::UnixPlatformService` в свободное время цикла спит по 2 мс;
такие вызовы не считаются циклами. VM запоминает фрейм метода, вызвавшего натив,
а имя метода берётся из отладочной информации scode (`debug="true"`). Если её нет,
считается каждый `Sys.sleep`, и в журнал пишется предупреждение.

Пример строки статистики при `scanPeriod=50`:

```
svm stats: cycles=41 period_ms_avg=50.103 period_ms_min=47.486 period_ms_max=52.675 overruns=0 late_ms_max=0.000 window_s=2.0 total_cycles=41 total_overruns=0
```

`overruns` — циклы, которые не уложились в `scanPeriod`; `late_ms_max` — на сколько
они опоздали. При работе под systemd отчёт также виден в `systemctl status` (STATUS=).

## Перегрузка цикла (`scan.resync`)

`App` вычисляет срок следующего цикла как `deadline += scanPeriod`. Если цикл
затянулся (долгий `work()`, сохранение, своп, заморозка процесса), срок
отстаёт, и в режиме `off` следующие циклы идут подряд без пауз, пока не догонят.
Логика, которая считает время в циклах, при этом искажается.

Проверка (`tests/svm_stage3_test.py`, VM заморожена на 2 с, `scanPeriod=50`):

| Режим | Циклов за ~6,5 с | Что видно |
|---|---|---|
| `off` | 132 (номинал) | серия циклов с периодом почти 0 |
| `skip` | 97 | 38 периодов пропущено, сетка сохранена |
| `now` | 92 | пропуски, новая сетка от момента восстановления |

Каждый пропуск попадает в журнал (`svm scan: overrun ...`, не чаще раза в 10 с) и в
статистику (`resyncs`, `skipped_periods`; перегрузки считаются в `overruns`).

## Modbus Master (`modbus.safe=1`)

В исходном коде найдены и при `modbus.safe=1` исправлены две проблемы:

1. **Изменения конфигурации точки терялись.** После запроса поток копировал
   в Sedona всю структуру регистра вместе с адресом, функцией и длиной из начала
   запроса. Если точку или устройство меняли во время запроса, изменение пропадало,
   и точка продолжала опрашивать старый регистр до перезапуска. При тесте с
   «молчащим» сервером (каждый запрос висит 100 мс) откатилось 4 изменения из 10.
   Теперь копируются только результат (data, status, done, request).
2. **Регистры удалённых точек не освобождались.** `removeRegister` был отключён
   (`return` в первой строке), видимо, из-за неправильного порядка блокировок в
   коде удаления. Теперь регистр помечается, поток опроса освобождает его,
   не держа `reg_mutex` при захвате `master_mutex`. Помеченные регистры
   освобождаются и при остановке сети. Под AddressSanitizer после 30 циклов
   «добавить точку, прочитать, удалить» ошибок памяти нет и утечек регистров нет
   (без опции утекает 30).

Без опции, независимо от неё, исправлен `memset` до проверки `malloc` на NULL в
`addRegister`.

## Утечки памяти (`mem.fixes=1`)

Найдены AddressSanitizer'ом (`tests/svm_stage3_test.py`, `test_mem_fixes_asan`):

- `double_getAST` / `bool_getAST`: при синтаксической ошибке в выражении буфер
  и сканер flex не освобождались. Утечка на каждый разбор выражения.
- `modbus_slave_clear`: `unregister_modbus_slave()` обнулял структуру до
  `modbus_mapping_free()`, и таблица регистров не освобождалась.

С `mem.fixes=1` ASan после работы с Modbus Master/Slave и неверным выражением
сообщает только о стеке и статических данных VM, которые живут до конца процесса.
Без опции исправлен порядок «memset до проверки malloc» в `addSlaveService`
(TCP и Serial).

## systemd: готовность и watchdog

Шаблон `install/sedonapro@.service` использует `Type=notify` и `WatchdogSec=30`:
- unit становится `active`, когда начинается первый цикл сканирования (`READY=1`);
- если цикл не пинговал 30 с, systemd убивает VM (SIGABRT) и перезапускает её
  (`Restart=on-failure`). В `systemctl show -p Result` будет `watchdog`.

Экземпляр соответствует каталогу `run/<экземпляр>`, поэтому несколько VM работают
независимо, каждая со своими портами в `app.sab`. Режим реального времени описан в
`install/realtime.conf.example`.

Текущая `sedonapro-sedona.service` (Type=simple) не меняется. В ней `READY` и пинги
не отправляются, потому что systemd не задаёт `NOTIFY_SOCKET`.

## Безопасный запуск (`safeboot.after=N`)

Файл `svm.boots` считает запуски подряд, которые не проработали
`safeboot.healthy.seconds`. Удачный запуск сбрасывает счётчик в 0.

| Запуск | Действие |
|---|---|
| 1 … N | обычный |
| N+1 | уровень 1: `app.sab` → `app.sab.safeboot1`, запуск с `app.sab.bak` (если он корректен и отличается) |
| N+2 … 2N | обычный |
| 2N+1 | уровень 2: `app.sab` → `app.sab.safeboot2`, запуск с `safeboot.app` (если задан) |
| далее | обычный; ограничение даёт `StartLimitBurst` systemd |

Исходное приложение не удаляется. Чтобы вернуть его, переименуйте `app.sab.safeboot1`
обратно в `app.sab`. Во время пробного периода обновления (`stage.rollback`) запуски
safeboot не считает: откатом занимается пробный период. Успешный откат сбрасывает
счётчик. Если неисправен сам `kits.scode`, а не приложение, safeboot не поможет;
для этого служит `stage.rollback`.

`safeboot.app` — это обычный `.sab`, скомпилированный `sedonac` из минимального `.sax`
(SOX, users, platform) с теми же портами и учётной записью, что у рабочего
приложения. Тогда контроллер останется доступен для ремонта.

## Атомарное сохранение (`save.atomic=1`)

- Файл, открытый на запись, пишется в `<имя>.tmp`. При закрытии выполняются `fflush`
  и `fsync`, для `.sab` проверяется формат, затем `rename` поверх `<имя>` и `fsync`
  каталога. Если что-то из этого не удалось, временный файл удаляется, а старый остаётся.
- `FileStore.rename` использует атомарный `rename(2)` вместо пары «удалить, затем
  переименовать».
- Резервная копия защищена: при `App.save` битый `app.sab` **не** перезаписывает
  исправный `app.sab.bak` (в журнале: `save.atomic: keeping app.sab.bak ...`).

## Поколения резервных копий (`save.keep=N`)

Перед тем как `App.save` переименует `app.sab` в `app.sab.bak`, старые копии
сдвигаются: `app.sab.bak.<N-2>` → `.<N-1>` … `app.sab.bak` → `app.sab.bak.1`
(через жёсткую ссылку, так что `app.sab.bak` есть в любой момент). Самая старая
копия удаляется. Работает и без `save.atomic`; при `save.atomic=1` битый `app.sab`
не сдвигает копии и не перезаписывает их. safeboot по-прежнему использует только
`app.sab.bak`; более старую копию возвращают вручную: остановить службу,
скопировать `app.sab.bak.K` в `app.sab`, запустить.

## Быстрая сборка (необязательно)

```sh
python3 build.py vm --fast    # -O3 и диспетчеризация computed goto
```

ABI и scode те же. На вычислительном тесте (30 млн итераций с вызовами методов
и float) `--fast` стабильно даёт 1,98–2,0 с. Обычная сборка — 3,0–3,75 с: время
колеблется от версии к версии из-за раскладки кода switch-интерпретатора.
Наборы тестов core и offline проходят и в обычной сборке, и с `--fast`.

```sh
python3 build.py all --arch amd64

python3 build.py verify --suite offline

```
