# Профессиональные kits SedonaPro

Правила, по которым написаны kits `sproBase`, `sproSignal`, `sproControl`,
`sproEquip` и следующие за ними (вентиляция, тепло, энергия). Цель — чтобы сотня
компонентов вела себя одинаково: инженер, разобравшийся с одним, понимает все.

Наборы для отраслей собираются ключом `--pack` (`profiles/packs/*.toml`):

```sh
./spro packs                         # какие есть
./spro build sim --pack control      # ESP32-профиль + регулирование
./spro build linux --pack pumps      # full + насосы
```

## Имена слотов

| Слот | Смысл |
|---|---|
| `in`, `in1`…`inN` | входы |
| `pv` | измеренное значение (process value) у регуляторов |
| `sp` | уставка |
| `out` | главный выход |
| `enable` | разрешение работы; `false` — выход в безопасное значение, `status = disabled` |
| `cmd` | команда на исполнительное устройство (пуск насоса) |
| `fb` | обратная связь от устройства (контактор, реле потока) |
| `fault` | вход аварии устройства (тепловое реле, авария ЧРП) |
| `mode` | `auto, hand, off` (`Pro.modeRange`) |
| `status` | общий код состояния (`Pro.statusRange`, ниже) |
| `reset` | действие сброса защёлкнутой аварии |

Вход, который приходит только по связи (измерение, запрос), — `property` без
`@config`: Sedona не хранит его в приложении. Всё, что человек задаёт руками, —
`@config`, в том числе уставки `sp` и `enable`: их тоже можно связать, но
заданное в редакторе значение переживёт перезапуск. Результат — `@readonly`. У каждого слота комментарий `**`: его
показывает редактор.

## Единицы

- Время в настройках — секунды, `float`, `@unit=Units.second`. Моточасы — часы.
- Выход на привод — проценты 0…100 (`outMin`/`outMax` по умолчанию 0 и 100).
- Температура °C, давление — кПа или бар (указано в `@unit`), расход м³/ч, мощность кВт.
- Пределы `@min`/`@max` у всех настроек, где значение может быть недопустимым.

## Общий status

Одно поле `status` с одним списком у всех компонентов — панель оператора, MQTT и
SCADA читают его одинаково:

| Код | Имя | Когда |
|---|---|---|
| 0 | `ok` | работает нормально |
| 1 | `disabled` | `enable = false` |
| 2 | `hand` | ручной режим |
| 3 | `off` | принудительно выключен |
| 4 | `inputBad` | неверный вход (NaN, обрыв, вне диапазона), используется замена |
| 5 | `fault` | авария оборудования |
| 6 | `alarm` | технологическая авария |
| 7 | `standby` | готов, не работает (нет запроса, резерв) |
| 8 | `starting` | идёт пуск |
| 9 | `stopping` | идёт останов (выбег, продувка) |
| 10 | `limited` | выход на ограничении |
| 11 | `config` | неверная настройка |
| 12 | `locked` | остановлен защёлкнутой аварией, ждёт сброса |
| 13 | `waiting` | ждёт условия (задержка, минимальное время простоя) |

## Неверные значения

Неверное аналоговое значение — `null` (NaN) или бесконечность, проверка
`Pro.valid(x)`. Компонент:

1. не пропускает NaN в интегратор, счётчик или фильтр — их состояние не портится;
2. выдаёт определённое значение (описано в комментарии компонента: держит последнее,
   уходит в безопасное или в `fallback`);
3. ставит `status = inputBad`.

## Время

Компоненты не зависят от периода сканирования: шаг считается по `Sys.ticks()`
через `Ticker`, вся логика — в методе `update(float dt)`. Тесты вызывают
`update(1.0f)` и за доли секунды прогоняют часы работы объекта. Шаг ограничен 10 с:
пауза VM в отладчике не сбрасывает интегратор и таймеры.

## Перезапуск и пропажа питания

- Настройки (`@config`) хранятся в приложении.
- Рабочие счётчики (моточасы, пуски, энергия) наследуют `Retained` и сохраняются
  `RetainService` — в файл раз в `interval` минут, при остановке и после ручного
  изменения. Без `RetainService` в приложении они начинают с нуля.
- Остальное состояние (интегратор, таймеры) после старта начинается заново, и
  компонент выходит из него без скачка (безударный старт).

## Ручной режим

Исполнительные компоненты (`Pid`, `Motor`, ...) имеют `mode` или стоят за `Hoa`.
В `hand` выход — `handValue`, автоматика следит за ним, и при возврате в `auto`
выход не прыгает.

## Совместимость

- После версии kit 1.0 имена и смысл слотов не меняются: приложения переносятся
  между версиями через `.sax` по именам.
- Новые слоты добавляются в конец класса.
- Изменения поведения — в `CHANGELOG` kit с указанием, как перенести.

## Память и ESP32

- Никакого `new` и динамической памяти; массивы фиксированного размера.
- Kit, который нужен на ESP32, собирается для `sim` и `esp32`; его тесты —
  чистый Sedona (`portable_tests = true` в `kit.toml`) и выполняются ещё и в
  симуляторе ESP32.

## Проверка

Каждый компонент:

- модульный тест в `test/` — нормальная работа, неверные входы, границы настроек;
- для регуляторов и автоматики — проверка на модели объекта (замкнутый контур),
  например выход PID на уставку без перерегулирования больше заданного;
- карточка в каталоге (`./spro catalog`) и строка в README kit.

Быстрый прогон тестов одного kit: `python3 tools/quicktest.py sproControl`
(после `./spro build linux`).

## Лицензия и происхождение

Код — Apache 2.0, с нуля. Поведение берём из инженерной практики и открытых
источников (учебники, стандарты, наши проекты); код и описания библиотек
производителей контроллеров не переносим.
